Architecture overview

Lacia

Lacia is a control system that keeps AI coding agents on track across long projects. It records what happened, works out what comes next from those records, and stops at set points for a person's decision.

What it does well

Long work survives the session

Each new session recomputes where the work stands from permanent records, so progress does not depend on chat memory.

Crashes do not repeat actions

When a crash leaves an action in doubt, Lacia marks it unknown and does not run it again.

Finished work stays checked

Status is computed from the records and file hashes, so work that has gone out of date shows up as stale.

People keep the key decisions

Seven named decisions wait for the user, and an agent's own tool call is rejected as approval.

Review is tested with data

On 18 real bug fixes, Lacia's reviewer found 65 of 74 serious bugs, against 41 for /code-review.

One design for two agents

Its CLI, MCP tools and skills for Claude Code and Codex come mainly from one catalog file.

The session loop

Lacia's policy fixes the steps of a session. The agent chooses the timing inside a step, and every step writes to the records. The next session starts from those records, which closes the loop.

The user decides at seven named points. Five are shown above. At any step the user can also answer the agent's questions or stop the work at once.

Plan structure

A plan holds the agreed work. Records hold what has happened to it. Keeping them apart lets Lacia recompute whether finished work still holds.

Main design decisions

Records are the source of truth

Plans, changes, completions and closures are written as records in the project repository. Each record's file name contains the hash of its content, and loading rejects a mismatch. Task state is worked out on each read by the first matching rule over the records.

Finished work is rechecked

A completion is computed as current, stale or invalid from digests of the task contract and its inputs. When an input changes later, the work shows up as stale.

A crash never causes a repeat

A request is saved as dispatching before its effect starts. If it dies there, it stays unknown until its original receipt is found or the user releases it with a recorded reason. Lacia does not run it again.

Context has a budget

Plan tasks get 32 KiB of context by default. Optional parts fall back to pointers. Required parts that do not fit stop the dispatch and are not cut silently.

Review is kept apart from the work

Reviewers run in an empty folder with read-only review tools. Above the low-risk tier, two finders read each part of a change: one sees the task, the other only the code. A verification call merges duplicates and drops only findings it shows wrong. A review that leaves a changed file unread counts as no review.

Installed files stay in step

If an installed entry file has drifted from the catalog, start verbs are refused until it is repaired.

Measured result

Two code reviewers ran side by side on 18 real bug fixes with the same AI model and effort.

32 bugs were found by both tools. Lacia's reviewer also saw each task's description. An AI of the same model family labeled the findings, and bugs both tools missed are not counted.

This comparison led to the current design of two reviewers plus a verification step.
